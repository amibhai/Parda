# PARDA — Glossary of Terms

This glossary defines terms used throughout PARDA's code, documentation,
and threat model. Entries are ordered alphabetically.

---

**Break-in Recovery**
A property of the Double Ratchet Algorithm: even if an attacker compromises a
session's current state (e.g., via device seizure), future messages remain
secure once new DH ratchet steps are performed. Contrast with *forward secrecy*,
which protects *past* messages.

**Cover Traffic**
Dummy messages injected into a mix network to prevent an adversary from
distinguishing real communication patterns from silence. Planned for Phase 2.

**Dead Drop**
An asynchronous, unaddressed message delivery mechanism: a sender deposits an
encrypted message at a shared location; the recipient retrieves it later without
direct contact. Used in PARDA's Phase 4 offline mesh mode.

**Delay-Tolerant Networking (DTN)**
A networking paradigm for environments with intermittent connectivity. Messages
are stored and forwarded by intermediate nodes until they reach the destination.
Used in PARDA Phase 4 for denied/degraded connectivity scenarios.

**Double Ratchet Algorithm (DR)**
The core session protocol in PARDA. Combines a *symmetric-key ratchet* (for
forward secrecy within a chain) with a *Diffie-Hellman ratchet* (for break-in
recovery between chains). Developed by Trevor Perrin and Moxie Marlinspike.
Reference: [Signal Specification](https://signal.org/docs/specifications/doubleratchet/).

**Dumb Pipe**
PARDA's relay server design principle: the server stores and forwards opaque
ciphertext envelopes without any ability to read, modify, or correlate their
contents. See `server/` and `docs/phase1-architecture.md §6`.

**Forward Secrecy (FS)**
A property guaranteeing that compromise of a long-term key does not expose
previously encrypted messages. In PARDA, achieved by deriving per-message
ephemeral keys that are deleted immediately after use.

**Global Passive Adversary (GPA)**
An adversary capable of observing all network traffic simultaneously, recording
packet timing, sizes, and routing information. The primary adversary class in
PARDA's threat model. See `docs/THREAT_MODEL.md §3.1`.

**Identity Key (IK)**
A long-term Ed25519 key pair that represents a user's identity. Used in X3DH
to authenticate the initial key exchange. In PARDA, the private IK never leaves
the platform hardware security module.

**libsignal-protocol**
The Signal Foundation's official Rust implementation of the Signal Protocol.
Used as PARDA's cryptographic core. Not published on crates.io; consumed as a
pinned git dependency from `github.com/signalapp/libsignal`.

**MessageEnvelope**
PARDA's wire message format. Contains the sender ID, recipient ID, base64-encoded
libsignal ciphertext, envelope type, timestamp, and (as of Sub-Phase 2A) a
`version` byte. `sealed_sender` is active as of Sub-Phase 2A (see below);
`routing_hint` (Sub-Phase 2B) and `self_destruct_at` (Phase 3) remain inactive
stubs.

**Mix Network**
A message routing architecture that defeats traffic analysis by shuffling
messages through a series of nodes, each of which re-encrypts and re-orders
packets before forwarding them. PARDA Sub-Phase 2B will implement a
Loopix-inspired Sphinx-packet mix network; not yet started.

**One-Time Prekey (OTPK)**
A Curve25519 key pair pre-generated and uploaded to the relay server. Consumed
exactly once during X3DH session initiation. Provides additional forward secrecy
for the initial message. PARDA generates a batch of 100 OTPKs on enrollment.

**PreKeyBundle**
A package of public key material uploaded by Bob to the relay server, allowing
Alice to initiate an X3DH session without Bob being online. Contains: identity
key, signed prekey, optional one-time prekey.

**Sealed Sender**
A Signal Protocol mechanism that hides the sender's identity from the relay
server inside the encrypted envelope, authenticated only by the recipient
after decryption via an embedded `SenderCertificate`. Implemented in
Sub-Phase 2A (`parda_protocol::sealed_sender`), using `libsignal-protocol`'s
own `sealed_sender_encrypt`/`sealed_sender_decrypt`. Hides the *sender_id*
field from the relay's logs/store/responses — it does not hide the sender's
IP address (see `docs/THREAT_MODEL.md` §3.5). `MessageEnvelope.sealed_sender`
defaults to `false`; a sender opts in per-message via
`SessionManager::encrypt_sealed`.

**Self-Destruct**
A mechanism that cryptographically erases a message's decryption key at a
configured time or on first read, making recovery impossible even with device
access. Planned for Phase 3. The `self_destruct_at` field in `MessageEnvelope`
is reserved for this purpose.

**Signed Prekey (SPK)**
A medium-term Curve25519 key pair signed with the identity private key.
Included in the PreKeyBundle and rotated periodically. The signature allows
Alice to verify that the prekey was genuinely generated by Bob.

**Sphinx Packet**
A fixed-size, onion-encrypted packet format designed for mix networks. Each
relay node strips one layer of encryption, learns only the next hop, and
re-randomises the packet before forwarding. Planned for Sub-Phase 2B; not yet
implemented.

**Store-and-Forward**
A message delivery pattern where the relay server holds encrypted envelopes
until the recipient polls for them. Used in PARDA's relay server since Phase 1;
as of Sub-Phase 2A the store is a SQLCipher database (encrypted at rest,
persists across restarts) rather than an in-memory queue.

**Trust-On-First-Use (TOFU)**
A key trust model in which a new identity key is automatically trusted on
first encounter and stored for future verification. PARDA Phase 1 uses TOFU.
Phase 2 will add out-of-band safety-number verification to harden this.

**X3DH (Extended Triple Diffie-Hellman)**
The key agreement protocol used to establish a shared session secret between
two parties who have not previously communicated. Alice uses Bob's PreKeyBundle
to compute a shared secret; Bob reconstructs the same secret on receiving the
first message. Defined in the
[Signal X3DH specification](https://signal.org/docs/specifications/x3dh/).
